# MISSION.md Format

`MISSION.md` lives at the workspace root. It captures _why_ the user is learning this topic. Every teaching decision — what to teach next, which resources to surface, and which exercises to design — should trace back to it.

## Template

```md
# Mission: {Topic}

## Why
{1–3 sentences. The concrete real-world goal the user is chasing. What changes in their life or work when they have this skill? Avoid abstract framings such as "to understand X"; identify the underlying outcome.}

## Success looks like
- {A specific, observable thing the user will be able to do}
- {Another specific thing}

## Constraints
- {Time, budget, prior commitments, learning preferences, or other bounds}

## Out of scope
- {Adjacent topics the user explicitly does not want to pursue now}
```

## Rules

- Keep one mission per workspace. Unrelated topics need separate workspaces.
- Prefer concrete outcomes: “Run a half marathon by October” is better than “get fitter.”
- Use `ask` to resolve vagueness before writing a mission; a bad mission is worse than none.
- When the user's goal changes, update the file rather than letting a stale mission steer future lessons.
- Keep the mission to one screen: it is a compass, not a plan.

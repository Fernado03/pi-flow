# Commit and Document

Commit only work the user explicitly approves. Preserve every unrelated working-tree and index change.

## Inspect and select

1. Use `bash` to read `git status --short`, `git diff --stat`, and `git diff --cached --stat`. Inspect targeted diffs before proposing a commit. If there are no changes, stop and report it.
2. Treat pre-existing staged paths as user-owned unless the user explicitly includes them. Never reset, unstage, amend, force, push, or otherwise alter unrelated work.
3. Propose a Conventional Commit message:

   ```text
   <type>(<scope>): <short imperative summary>
   ```

   Use `feat`, `fix`, `refactor`, `docs`, `chore`, `test`, `style`, or `perf`; keep the summary under 70 characters.
4. Show the proposed message, exact intended paths, and any suspected secret paths. Use `ask` to obtain approval of both the message and explicit path list. Tests and documentation are eligible whenever the user selects them; never exclude either category by default. Do not stage suspected secrets.

## Stage and commit

1. Stage only approved, non-secret paths with `git add -- <path>...`; never use a broad add command.
2. Reinspect only the intended staged paths. Use `ask` for final confirmation if their staged contents differ from the approved summary.
3. Commit only the intended paths with `git commit --only -m "<approved message>" -- <path>...`, so unrelated staged work remains staged and uncommitted. Capture the short and full hashes.

## Optional issue action

If the message contains a closing reference or bare `#N`, use `ask` whether to post a comment or close the issue after the commit. With no reference, ask once whether an issue should be linked. Before using GitHub tooling, verify that a GitHub remote and `gh` are available. Post this comment before any close action:

```markdown
> *This was generated by AI during commit.*

Linked from commit `<short-hash>`: <commit subject>
```

If commenting fails, report the failure and do not close the issue.

## Local record and documentation risk

1. Write a dated record at `.pi-flow/journal/<YYYY-MM-DD>/<HH-MM>-<slug>.md`, unless the user declines a local record. Include the full hash, summary, what changed, why, and any follow-up worth preserving. Do not stage it unless explicitly selected.
2. Read `.pi-flow/CONTEXT.md` when present. If the committed paths overlap a documented public surface, use `ask` whether to run `/pi-update-docs`; never modify documentation automatically.

## Completion

Report the commit hash and message, paths committed, intentionally preserved paths, local-record path or opt-out, issue action, and any documentation follow-up. Do not claim that unselected tests or docs were excluded; name only what was actually selected or preserved.

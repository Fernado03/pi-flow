# Triage

Move issue-tracker requests through a small, explicit state machine. Read tracker configuration and `.pi-flow/CONTEXT.md` first; if label mapping is absent, ask the maintainer to supply it or run `/pi-setup-pi-flow`.

Every tracker comment created during triage MUST begin:

```markdown
> *This was generated by AI during triage.*
```

A pull request is triaged like an issue with an attached diff when tracker configuration includes external pull requests. Resolve a bare `#42` according to that configuration.

## States

Apply exactly one category and one state:

- Categories: `bug`, `enhancement`.
- States: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`.

An unlabeled request normally enters `needs-triage`; `needs-info` returns there after a reporter reply. Conflicting state labels or an unusual transition requires an `ask` decision from the maintainer. The maintainer may override any recommendation.

`ready-for-agent` means an implementation brief is attached. For a pull request, it means a worker can continue the existing diff; `ready-for-human` means human judgment, access, design, or merge work remains.

## Attention queue

Query the configured tracker and show oldest first:

1. Unlabeled requests.
2. `needs-triage` requests.
3. `needs-info` requests with reporter activity after the last triage note.

When pull requests are included, tag each line `[PR]` or `[issue]`; include only external pull requests in discovery. Show counts and one-line summaries, then use `ask` to let the maintainer choose what to inspect.

## Specific issue or pull request

1. Gather the full body, comments, labels, author, dates, prior triage notes, and—when relevant—the diff. Read applicable domain guidance and `.pi-flow/CONTEXT.md` plus related `.pi-flow/docs/adr/` records.
2. Check redundancy by searching for the requested behavior by domain concept, and report where you looked. If it already exists, recommend `wontfix` as already implemented. Read matching `.pi-flow/out-of-scope/*.md` files for prior rejections.
3. Recommend a category and state with the relevant codebase evidence. Use `ask` before changing labels, posting a comment, closing anything, or making another material maintainer decision.
4. Verify the claim before specification work: reproduce a reported bug; for a pull request, confirm the diff's claimed behavior with the smallest relevant check. Report confirmed, failed, or insufficient detail.
5. If material requirements remain unclear, use `ask` one question at a time. Use a `task` batch only for independent, substantial investigation; preserve resolved terminology in `.pi-flow/CONTEXT.md` or an applicable `.pi-flow/docs/adr/` record.
6. Apply the approved outcome:
   - `ready-for-agent`: post a brief following [AGENT-BRIEF.md](AGENT-BRIEF.md).
   - `ready-for-human`: post the same shape and state why human work is required.
   - `needs-info`: post the note template below.
   - `wontfix`: for an existing implementation, point to it without creating an out-of-scope record; for a rejected enhancement, update the matching record using [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md), comment, then close; for a rejected bug, explain and close.
   - `needs-triage`: apply the state and optionally record partial progress.

## Direct state changes

When a maintainer asks to move a named request to a state, summarize the exact labels, comment, and close action, then use `ask` for confirmation before applying them. Skip unnecessary discovery. When moving to `ready-for-agent` without a brief, ask whether to write one.

## Needs-info note

```markdown
## Triage Notes

**What we've established so far:**

- established fact

**What we still need from you (@reporter):**

- specific, actionable question
```

Keep resolved information; never re-ask answered questions.

## Completion

Report the requests triaged, the approved outcomes applied, any remaining blocker, and the next recommended Pi Flow action.
